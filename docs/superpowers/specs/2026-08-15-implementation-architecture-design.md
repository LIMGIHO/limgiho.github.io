# 실제 구현 범위 중심 아키텍처 설계

## 목적

현재 대표 사례 섹션은 경력기술서의 문제·제약·역할·성과를 반복하고, 단순 Before/After 그림은 실제 구현 범위를 설명하지 못한다. 기존 `architecture.html`에 있던 구체적인 애플리케이션, 실행 경로, 외부 경계와 배포 구조를 다시 사용해 방문자가 무엇을 구현했는지 한 화면에서 파악할 수 있게 한다.

## 섹션 구성

- `02 · FLAGSHIP CASE`를 `02 · 통합 업무 플랫폼 개발`로 바꾼다.
- 제목은 `통합 업무 플랫폼 개발`로 통일한다.
- 문제, 제약, 역할, Outcomes, Supporting Evidence 블록을 제거한다.
- 기존의 단순 Before/After SVG와 설계 판단 카드 10개를 화면에서 제거한다.
- 섹션은 `구현 범위 요약`, `시스템 구성`, `구현 상세` 세 부분으로 구성한다.

## 구현 범위 요약

첫 화면에는 문장 대신 다음 사실을 짧은 항목으로 표시한다.

- 15종 운영 시스템 분석과 기능 이관
- 90여 개 업무 화면 개발
- 5개 업무 도메인 구성
- 8종 외부 시스템 연동
- API·Queue·Worker·Batch 분리 운영
- 변경 앱 기반 CI/CD 구성

## 시스템 구성

기존 `architecture.html`의 노드와 연결을 익명화해 다음 구조로 표시한다.

```text
Web · Next.js
90여 개 업무 화면 / 화면·도메인 슬라이스
                │ REST
API · NestJS ───┼── Legacy API · Express
5개 업무 도메인 │   모듈 단위 점진 이관
                │
      ┌─────────┼─────────────┐
Queue · BullMQ  External      Local LLM
업무별 작업 큐   외부 연동 8종   문서 추출·OCR
      │
Worker · Cron
예약 작업·분산 락
      │
Batch
스크래핑·FTP·엑셀

Data
Oracle · MySQL · PostgreSQL · ODBC

CI/CD
변경 앱 감지 → Test → Kaniko Build → Swarm Deploy
```

데스크톱에서는 연결 관계가 보이는 시스템 맵으로 표시한다. 모바일에서는 같은 내용을 실행 순서와 역할이 유지되는 세로 카드로 표시하며 가로 스크롤을 만들지 않는다.

이 맵의 최우선 목적은 기술 목록이 아니라 설계한 구조를 설명하는 것이다. 따라서 다음 경계를 시각적으로 구분한다.

- Presentation: Web
- Application: API와 병행 운영 중인 Legacy API
- Async execution: Queue, Worker, Batch
- Integration & data: External, Local LLM, Data
- Delivery: CI/CD

경계 상자는 단순 묶음이 아니라 각 컴포넌트의 책임이 어디에서 끝나는지 보여줘야 한다. 앱, 인프라, 외부 경계, 레거시, 배포 파이프라인은 서로 다른 선 스타일과 범례로 구분한다.

## 실행 흐름

한 개의 화살표로 모든 것을 뭉뚱그리지 않고 다음 네 흐름을 분리해 표시한다.

1. 동기 요청: `Web → API → Data / External / Local LLM`
2. 비동기 작업: `API → Queue → Worker → Batch / External`
3. 점진 이관: `Legacy API ⇢ API`를 점선으로 표시
4. 배포: `변경 감지 → Test → Kaniko Build → Swarm Deploy`를 런타임 맵과 분리된 하단 레일로 표시

연결선에는 `REST`, `enqueue`, `consume`, `repository`, `port/adapter`, `internal HTTP`, `job execution`처럼 실제 계약이나 호출 방식을 적는다. 선이 교차해 흐름을 가리지 않도록 동기 흐름은 중앙 세로축, 비동기 흐름은 오른쪽, 통합·데이터 경계는 왼쪽과 하단에 배치한다.

## 아키텍처 표현 원칙

- 각 노드에는 이름만 쓰지 않고 `기술`, `책임`, `배포 단위`를 함께 표시한다.
- Web과 API는 핵심 애플리케이션으로 강조한다.
- Legacy API는 제거 완료가 아니라 병행 운영·모듈 단위 이관 중임을 점선으로 표현한다.
- Queue와 Worker는 서로 다른 배포 단위이며 공통 잡 계약으로 연결된다는 사실을 표시한다.
- External은 HTTP, FTP, EDI, 소켓을 하나의 프로토콜로 추상화한 것처럼 보이지 않게 하며, 포트·어댑터의 위치만 통일했다는 점을 표시한다.
- Local LLM은 외부 SaaS가 아니라 사내 추론 경계이고, 선택적 OCR과 JSON Schema 검증이 포함됨을 표시한다.
- Data는 단일 DB처럼 그리지 않고 Oracle, MySQL, PostgreSQL, ODBC 공존과 리포지토리 경계를 표시한다.
- CI/CD는 런타임 호출선과 섞지 않고 빌드·배포 흐름으로 분리한다.
- 장식 목적의 애니메이션은 넣지 않는다. 선택 강조와 상세 패널 갱신에 필요한 최소 전환만 사용한다.

## 구현 상세

시스템 맵의 각 노드는 다음 세 필드만 가진다.

- `구현`: 직접 만든 기능과 담당 범위
- `구조`: 코드·프로세스·배포 단위의 구성
- `운영`: 실제 운영 시 실행 방식 또는 효과

노드별 내용은 다음과 같다.

- Web: Next.js 기반 90여 개 업무 화면, 화면 로컬 슬라이스와 공용 도메인 슬라이스
- API: NestJS 기반 단일 진입점, 5개 업무 도메인과 포트·어댑터 경계
- Legacy API: Express API를 유지하면서 도메인 모듈 단위로 이관
- Queue: Redis·BullMQ 기반 업무별 비동기 작업 큐와 공통 계약
- Worker: 예약 실행, 큐 소비, Redis 분산 락을 담당하는 별도 배포 단위
- Batch: 스크래핑, FTP, 엑셀과 장시간 작업을 API 프로세스에서 분리
- External: HTTP, FTP, 소켓, EDI 등 8종 외부 연동을 어댑터 경계로 분리
- Local LLM: 사내 추론 서버, JSON Schema 출력, 텍스트 판정 후 선택적 OCR
- Data: Oracle, MySQL, PostgreSQL, ODBC를 리포지토리 뒤에서 처리
- CI/CD: 변경 앱 감지, 테스트 게이트, Kaniko 이미지, Swarm 배포

기본 화면에서는 모든 노드의 한 줄 역할이 보인다. 상세 정보는 노드를 선택하거나 키보드로 활성화하면 한 개의 상세 패널에 표시한다. 별도의 문제·대안·선택·결과 서술은 표시하지 않는다.

상세 패널은 선택한 노드에 대해 다음도 함께 보여준다.

- 상위 입력과 하위 출력
- 다른 컴포넌트와 공유하는 계약
- 내부 디렉터리 또는 프로세스 구조
- 독립 배포 여부

이 정보로 시스템이 단순한 기술 조합이 아니라 책임, 경계, 계약과 배포 단위를 기준으로 설계됐다는 점이 드러나야 한다.

## 데이터와 익명화

- 시스템명, 고객사명, 내부 URL과 주소는 표시하지 않는다.
- 이전 아키텍처의 구체적인 공급자·기관 명칭은 `공공 API`, `상용 EDI`, `거래처 EDI`, `운송 시스템`, `하드웨어 소켓`, `FTP/SFTP`, `인증`, `메일`처럼 범주화한다.
- 경력기술서용 장문 필드는 화면 데이터에서 제거하고 노드별 구현 정보가 canonical data가 된다.
- 기본 Ice Blue와 카카오 Graphite Yellow는 같은 구조를 공유하고 강조 색만 다르게 사용한다.

## 검증

- Jekyll 빌드와 익명화 검증이 통과해야 한다.
- 두 프로필에 10개 구현 노드와 핵심 연결이 모두 렌더링되어야 한다.
- `FLAGSHIP CASE`, `문제`, `제약`, `OUTCOMES`, `SUPPORTING EVIDENCE`, `ENGINEERING DECISIONS`가 새 섹션에 없어야 한다.
- 노드 선택은 마우스와 키보드에서 동작하고 선택 상태와 상세 패널이 연결되어야 한다.
- 동기 요청, 비동기 작업, 점진 이관, 배포의 네 흐름이 서로 구분되어야 한다.
- 모든 연결선에는 호출 방식 또는 계약명이 있어야 한다.
- 앱, 인프라, 외부 경계, 레거시, 배포 유형의 범례가 있어야 한다.
- JavaScript가 비활성화되어도 각 노드의 한 줄 구현 범위는 읽을 수 있어야 한다.
- 데스크톱과 모바일에서 가로 넘침과 콘솔 오류가 없어야 한다.
- 이번 작업에서는 PDF를 생성하거나 검증하지 않는다.

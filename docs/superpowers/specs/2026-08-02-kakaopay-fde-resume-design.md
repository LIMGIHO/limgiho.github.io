# 카카오페이 FDE 전용 이력서 설계

작성일: 2026-08-02

## 목적

카카오페이의 `FDE - 전사 주요 프로젝트 지원 및 AI 기반 업무 생산성 향상` 포지션에 맞춘 별도 이력서를 만든다. 기존 범용 이력서는 유지하고, 이번 지원에서 판단에 필요한 경험만 다시 선별한다.

이력서의 중심은 AEPOS 단일 프로젝트가 아니다. KWE 입사 후 파편화된 레거시 시스템을 하나의 운영 플랫폼으로 통합해 온 장기 흐름과, 그 기반 위에서 AI를 이용해 MVP의 구현 비용과 리드타임을 낮추고 현업 피드백과 예외 발견을 앞당긴 현재의 개발 방식을 함께 보여준다.

## 핵심 포지셔닝

제목은 다음 방향을 사용한다.

> Software Engineer | Enterprise Platform · AI-enabled Delivery · Automation

첫 문장은 다음 의미를 담는다.

> 파편화된 현업 업무를 하나의 운영 플랫폼으로 전환하고, AI로 동작하는 MVP를 빠르게 제공해 요구사항과 예외를 현장에서 발견하며 더 나은 시스템으로 발전시켜 온 엔지니어

AI를 별도 기술 분야로 과장하지 않는다. 현업 문제를 정의하고 구현·배포·검증하는 기존 역량에 AI가 어떻게 더 빠른 피드백 루프를 만들었는지 설명한다.

## 전달할 서사

KWE 경력을 하나의 장기 프로그램으로 묶어 네 단계로 제시한다.

1. 통합 방향 수립
   - 15종 이상의 파편화된 프로그램과 이기종 DB 분석
   - 항공·해운·재무 등 핵심 업무 도메인 중심의 통합 방향 수립
2. 운영 플랫폼 구축
   - Next.js·Node.js·PostgreSQL 기반 웹 플랫폼 전환
   - 외부 시스템 연동, 데이터 마이그레이션, RPA·스크래핑 자동화
3. 개발·운영 기반 정비
   - Express에서 NestJS로 구조화
   - Worker·Redis·BullMQ, 테스트, CI/CD, 컨테이너 배포 체계 도입
4. AI 기반 고속 MVP와 업무 개선
   - AI 에이전트를 설계·구현·테스트·문서화에 활용
   - 동작하는 MVP를 빠르게 현업에 제공하고 실제 데이터에서 예외를 발견
   - Local LLM 문서 추출, R&R 검색, 문서 대조 등 업무 AI 적용
   - 규칙 기반 처리, LLM, 사용자 확정을 문제 특성에 따라 조합

## 공고의 두 업무와 연결

### 전사 주요 프로젝트 지원

- 모호한 현업 요구를 업무 흐름과 데이터 모델로 구체화
- 프론트엔드, 백엔드, 데이터, 인프라를 넘나들며 End-to-End로 구현
- 여러 부서와 외부 시스템이 얽힌 프로젝트를 운영 가능한 상태까지 마무리

### AI 기반 업무 생산성 향상

- AI 에이전트로 MVP 제작 주기를 줄여 더 많은 가설을 검증
- Local LLM을 실제 업무 문서와 내부 검색에 적용
- 실제 샘플, 반복 평가, 테스트, fallback으로 AI 결과를 검증
- 사용자가 최종 판단해야 하는 지점을 명확히 남기는 human-in-the-loop 설계

## 대표 근거

이력서에는 아래 근거를 우선 사용한다.

1. KWE 통합 운영 플랫폼 전환
   - 15종 레거시를 5개 핵심 업무 단위로 통합
   - 수작업 10분을 5초 이내로 단축
   - RPA로 월 1,200시간 상당의 반복 작업 절감
   - 1,000만 건 Oracle → PostgreSQL 마이그레이션과 정합성 검증
2. AI 에이전트 기반 MVP·개발 생산성 체계
   - agent 아카이브의 설계·구현·검증 기록
   - 작은 수직 기능 단위의 계획, 테스트, 완료 근거 누적
   - 실제 완료 건수와 기간은 사용자 확인 후 수치로 사용
3. Local LLM 기반 업무 솔루션
   - 수출신고필증 PDF 비동기 추출과 반복 평가
   - 문서 단위 문맥 보존, 부분 성공, 실패 관측성
   - R&R 검색에서 deterministic 후보 내 reranking과 안전한 fallback
4. 빠른 MVP를 통한 요구사항 발견
   - 삼성 전세기 실물 문서 분석과 대조 기능
   - AEPOS 실제 데이터 기반 화면 E2E harness
   - OneDrive 문서 자동화의 독립 MVP 선검증

## 문서 형식

기존 5페이지 PDF를 수정하지 않고, 별도의 3페이지 단일 컬럼 PDF를 만든다. 복잡한 사이드바, 프로필 이미지, 장식용 아이콘은 사용하지 않는다. ATS와 사람이 모두 빠르게 읽을 수 있는 구조를 우선한다.

### 1페이지: 지원 판단

- 이름, 연락처, GitHub, 상세 경력 링크
- 포지셔닝 제목과 소개 문장
- 공고의 두 업무에 대응하는 핵심 강점
- KWE Transformation Journey 네 단계
- 검증된 대표 수치

### 2페이지: Selected Evidence

아래 세 사례를 `문제 → 판단 → 구현 → 검증 → 변화` 순서로 기술한다.

1. 통합 운영 플랫폼 전환 프로그램
2. AI 에이전트 기반 MVP·개발 생산성 체계
3. Local LLM 기반 현업 문서 자동화

AEPOS와 삼성 전세기 프로젝트는 독립 대표 프로젝트가 아니라 두 번째와 세 번째 사례를 뒷받침하는 구체적인 장면으로 사용한다.

### 3페이지: 경력과 기술 기반

- KWE와 ILJIN 경력 요약
- Backend, Frontend, Data, Operations, AI
- 이전 주요 프로젝트와 수상
- 개인 프로젝트와 상세 자료 링크

## 시각 원칙

- 흰 배경과 검정·짙은 회색 본문
- 노란색은 핵심 수치와 구분선에만 제한적으로 사용
- 본문은 10pt 이상, 충분한 행간과 페이지 여백 확보
- 한 섹션당 불릿 수를 줄이고 문장 길이를 섞어 읽는 리듬 유지
- 페이지 번호와 짧은 푸터 사용

## JVM 경험 표현

사용하지 않은 Java/Kotlin을 기술 목록에 넣지 않는다. 이력서 상단에서 부족한 경험을 먼저 강조하지도 않는다.

대신 VB6 → C#/.NET → Node.js/NestJS로 주력 스택을 전환하면서 DI, 도메인 분리, 트랜잭션, 비동기 처리, 테스트, 운영 설계를 축적한 경험을 `Stack Adaptability`로 제시한다.

지원서에서 Java/Kotlin 경험을 직접 묻는 경우에는 운영 경험이 없음을 밝히고, 여러 차례의 스택 전환과 엔터프라이즈 백엔드 경험을 근거로 빠른 적응력을 설명한다.

## 문체 원칙

- 사실, 수치, 고유명사를 임의로 추가하거나 바꾸지 않는다.
- 추상적인 자기평가보다 실제 판단과 행동을 쓴다.
- `혁신`, `극대화`, `완성`, `시사한다` 같은 과장된 표현을 피한다.
- 영어 병기와 괄호를 줄이고 필요한 기술명만 유지한다.
- 모든 사례를 똑같은 문장 구조로 맞추지 않는다.
- AI 도구 이름보다 업무 과정과 검증 결과를 먼저 쓴다.
- 최종 문안은 `humanize-korean` 기준으로 보수적으로 윤문한다.

## 검증 기준

- 공고의 두 업무가 1페이지에서 모두 드러난다.
- KWE 경력이 개별 프로젝트 모음이 아니라 장기 변화의 흐름으로 읽힌다.
- AI 개발 생산성과 제품 내 AI 적용을 구분해 설명한다.
- AI 사례마다 실제 업무 문제, 구현 범위, 검증 또는 fallback이 있다.
- 확인되지 않은 생산성 수치나 완료 건수를 사용하지 않는다.
- Java/Kotlin 경험을 암시하거나 과장하지 않는다.
- PDF 렌더링 후 잘림, 지나치게 작은 글자, 빈 페이지가 없다.

# 기업 제출형 엔지니어 포트폴리오 설계

- 작성일: 2026-08-15
- 대상 저장소: `limgiho.github.io`
- 상태: 구현 전 승인 설계

## 1. 목적

기존 GitHub Pages 이력서를 기업 지원서에 첨부할 포트폴리오로 전면 개편한다. 이 자료는 방문자를 모으거나 서비스를 홍보하는 랜딩 페이지가 아니다. 경력기술서에 적힌 핵심 성과를 채용담당자와 개발 리더가 짧은 시간 안에 확인하고, 면접에서 설계 판단을 더 깊게 질문할 수 있도록 돕는 보충 자료다.

포트폴리오가 전달할 중심 문장은 다음과 같다.

> 복잡한 운영을 하나의 흐름으로 바꾸는, 플랫폼·통합에 강한 풀스택 엔지니어

지원 직무에 따라 첫 문장과 프로젝트 강조 순서는 바꿀 수 있지만, 프로젝트의 사실과 본문 구조는 공통으로 유지한다.

## 2. 성공 기준

1. 첫 화면에서 10초 안에 지원자의 포지셔닝, 대표 성과, 경력기술서 링크를 파악할 수 있다.
2. 1분 안에 대표 프로젝트의 문제, 담당 역할, 핵심 판단, 결과를 읽을 수 있다.
3. 채용담당자에게는 경력 흐름과 성과가, 개발 리더에게는 아키텍처와 트레이드오프가 보인다.
4. 같은 콘텐츠에서 일반 지원본과 카카오 지원본을 생성한다.
5. URL과 A4 PDF가 같은 정보 구조와 시각적 인상을 유지한다.
6. 모바일, 데스크톱, 인쇄 환경에서 핵심 콘텐츠가 잘리거나 숨겨지지 않는다.
7. 고객사, 내부 조직, 내부 시스템 고유명은 공개하지 않는다.

## 3. 범위

### 포함

- 기존 루트 이력서 페이지를 기업 제출형 포트폴리오로 교체
- 대표 사례: 15종 레거시 시스템의 통합 플랫폼 전환
- 보조 사례: 반복 업무 자동화
- 대표 사례의 보강 근거: 1,000만 건 이상 DB 마이그레이션, 배포 표준화, 백엔드 구조 전환
- `assets/portfolio/architecture.html`의 구조도와 설계 판단을 대표 사례에 통합
- `Career Journey` 경력 타임라인
- 일반 지원본과 카카오 지원본 프로필
- 웹 URL과 PDF 출력
- 하단의 간결한 `Additional Work` 개인 프로젝트 목록
- 익명화, 링크, 반응형, PDF 출력 검증

### 제외

- 서비스 소개, 의뢰 유도, 상담 신청, 영업형 문의 폼
- 숙련도를 퍼센트나 막대로 표현하는 기술 목록
- 로그인, 서버 API, 실시간 데이터, 콘텐츠 관리 화면
- React 또는 Next.js 기반 SPA 전환
- 지원 회사마다 본문을 복제해 별도 관리하는 구조
- 독립된 `architecture.html` 유지

## 4. 정보 구조와 분량

전체 페이지는 제출 문서형 단일 컬럼을 기본으로 한다. 대표 프로젝트 내부만 사례 연구처럼 깊게 구성한다.

### 4.1 Hero와 Career Snapshot — 약 15%

- 이름과 직무 포지셔닝
- 한 문장의 문제 해결 관점
- 대표 수치 3~4개
- 경력기술서 PDF와 GitHub 링크
- 이 자료가 경력기술서의 대표 프로젝트를 보충하는 문서라는 짧은 안내

상단 수치는 공통 콘텐츠에서 가져오되 지원 프로필이 노출 순서를 정한다. 수치는 경력기술서 또는 기존 프로젝트 자료로 확인할 수 있는 값만 사용한다.

### 4.2 Career Journey — 약 15%

연도순 경력 나열이 아니라 역할이 어떻게 확장됐는지를 보여준다.

1. ILJIN Global: MES 개발과 생산 데이터 기반 업무 시스템
2. 해외 공장 고도화와 프로젝트 리드
3. KWE Korea: 업무 자동화와 외부 시스템 연동
4. 레거시 통합 플랫폼 설계와 운영
5. 배포, 테스트, 데이터 전환을 포함한 플랫폼 책임 확장

웹에서는 스크롤 진입에 맞춰 타임라인 선과 카드가 순차적으로 강조된다. JavaScript가 없거나 PDF로 출력할 때는 모든 항목이 처음부터 완전하게 보인다.

### 4.3 대표 사례 — 약 50%

제목은 `15종 레거시 시스템을 단일 플랫폼으로`로 한다. 다음 순서로 읽힌다.

1. **문제**: 파편화된 프로그램, 이기종 DB, 중복된 업무 흐름과 유지보수 한계
2. **제약**: 매일 사용하는 운영 시스템이므로 전면 중단이나 일괄 재작성 불가
3. **나의 역할**: 분석, 구조 설계, 구현, 단계적 전환, 운영을 구분해 명시
4. **Before/After 구조**: 기존 15종 시스템이 5개 업무 도메인의 웹 플랫폼으로 수렴하는 구조
5. **핵심 판단**: 문제·대안·선택·결과 형식의 설계 카드
6. **성과**: 시스템 수렴, 업무 시간 단축, 운영 안정성, 변경 범위 통제
7. **근거 프로젝트**: DB 마이그레이션, NestJS 전환, CI/CD 표준화는 별도 대형 사례가 아니라 대표 사례의 신뢰 근거로 연결

기존 `architecture.html`에 있는 10개 설계 판단은 모두 보존하되, 첫 화면에는 가장 강한 3개를 우선 노출한다.

- 한 번에 갈아엎지 않은 점진적 전환
- 폴더 규칙이 아니라 타입으로 지킨 경계
- Worker 계약을 빌드 단계에서 검증한 방식

나머지 판단은 웹에서 펼쳐 읽을 수 있는 카드로 배치한다. PDF에서는 핵심 문장이 누락되지 않도록 모두 펼치되, 설명을 압축하여 페이지 수를 통제한다.

### 4.4 업무 자동화 사례 — 약 20%

`삼성 NERP`와 같은 고객·시스템 고유명은 사용하지 않고 `외부 업무 시스템 입력 자동화`처럼 역할명으로 바꾼다.

사례는 다음 순서로 구성한다.

1. 반복 수작업과 휴먼 에러 문제
2. 입력 전 문서 검증
3. RPA 처리 및 외부 시스템 연동
4. 실패 감지, 예외 처리, 재처리 흐름
5. 월 기준 업무 시간 절감과 운영 결과

단순히 봇을 만들었다고 설명하지 않고, 무인으로 계속 운영할 수 있도록 검증과 예외 흐름을 설계한 경험을 강조한다.

### 4.5 Experience, Technology, Additional Work

- 회사별 역할과 대표 결과를 2~3줄로 요약
- 기술은 숙련도 수치 없이 실제 프로젝트 사용 맥락으로 묶음
- 개인 프로젝트는 제목, 한 줄 목적, 핵심 기술, 링크만 표시
- 특정 지원 직무와 관련 있는 개인 프로젝트만 프로필 설정으로 상단 노출 가능

## 5. 시각 설계

### 5.1 공통 원칙

- 흰색 문서 바탕, 넓은 여백, 명확한 섹션 번호
- 장식보다 제목, 수치, 구조도, 설계 판단의 위계에 집중
- 카드 남용을 피하고 경계선과 배경색은 의미가 있을 때만 사용
- 영업형 문구, 과장된 애니메이션, 스킬 게이지, 문의 폼 제외
- 본문은 한국어 중심이며 영문은 짧은 섹션 라벨과 기술명에만 사용

### 5.2 기본 테마: Ice Blue

- 기본 배경: 흰색
- 보조 배경: 매우 연한 아이스 블루
- 핵심 강조: 중간 명도의 블루
- 본문: 짙은 그래파이트
- 용도: 일반 기업 제출본

아이스 블루는 넓은 면을 강하게 채우지 않는다. 왼쪽 문서선, 섹션 라벨, 링크, 구조도의 통합 영역과 핵심 판단 경계에 제한적으로 사용한다.

### 5.3 카카오 테마: Graphite Yellow

- 기본 배경과 본문 구조는 일반본과 동일
- 아이스 블루 의미 토큰만 낮은 채도의 옐로와 그래파이트로 치환
- 포지셔닝은 `Frontend · Platform · Integration`에 가깝게 조정
- 상단 지표는 업무 화면 수, 시스템 통합, 타입 기반 경계 등 프론트엔드 직무 관련 근거를 우선 배치

카카오 지원본은 새 페이지를 복제해 만드는 것이 아니라 지원 프로필을 선택해 생성한다.

- 기술 스택과 직접 수행한 설계 판단
- 보안 문제가 없고 근거를 확인할 수 있는 성과 수치

### 익명화

- 고객사명
- 고객 시스템명과 내부 시스템 고유명
- 사내 조직명
- 서버명, 데이터베이스명, URL, 계정, 네트워크 구조
- 외부 업체와 계약 관계를 특정할 수 있는 표현

예시는 다음과 같다.

| 원문 성격 | 포트폴리오 표기 |
| --- | --- |

구현 시 검증 스크립트가 공개 금지어 목록을 검사한다. 단, 재직 회사명은 허용 목록으로 관리한다.

## 7. 기술 구조

Jekyll이 정적 HTML을 생성하고 CSS와 작은 Vanilla JavaScript가 상호작용을 담당한다. Next.js나 React는 도입하지 않는다.

### 7.1 파일 책임

```text
_data/
  portfolio.yml            프로젝트 사실, 경력, 설계 판단, 링크
  portfolio_profiles.yml   default·kakao 노출 순서와 문구·테마 설정

_layouts/
  portfolio.html           페이지 전체 골격과 메타데이터

_includes/portfolio/
  hero.html                포지셔닝, 지표, CTA
  journey.html             Career Journey
  flagship.html            대표 사례
  architecture.html        Before/After 구조도
  decision-card.html       문제·대안·선택·결과
  automation.html          자동화 사례
  experience.html          경력과 기술
  additional-work.html     개인 프로젝트

assets/css/
  portfolio.scss           화면·반응형·인쇄 스타일과 의미 기반 테마 토큰

assets/js/
  portfolio.js             타임라인 강조와 설계 카드 펼침

index.md                    default 프로필 진입점
applications/2026-08-03/kakaopay-fde/portfolio/index.md
                            kakao 프로필 진입점

scripts/
  build-portfolio-pdf.sh   프로필별 PDF 생성
  verify-portfolio.py      콘텐츠·레이아웃·PDF 검증
```

각 페이지의 front matter는 `portfolio_profile`만 선택한다. 레이아웃은 이 값을 사용해 `portfolio_profiles.yml`에서 테마, Hero 문구, 지표 순서, 사례 강조 순서를 읽는다.

### 7.2 데이터 흐름

```text
portfolio.yml ─────────────┐
                          ├─ Jekyll/Liquid ─ HTML ─ URL
portfolio_profiles.yml ───┘                    └─ Chromium 인쇄 ─ PDF
```

프로필은 콘텐츠를 덮어쓰지 않는다. 다음 항목만 참조 또는 재정렬한다.

- 테마 이름
- Hero 포지셔닝 문장
- 상단 지표 식별자와 순서
- 대표 사례의 설계 판단 노출 순서
- 직무 관련 개인 프로젝트 노출 여부

이 규칙으로 일반본의 사실 수정이 모든 지원본에 자동 반영되게 한다.

### 7.3 Career Journey 동작

- HTML에는 모든 경력 항목을 연도순으로 렌더링한다.
- `IntersectionObserver`가 화면에 들어온 항목에 활성 클래스를 붙인다.
- 애니메이션은 장식적 강조일 뿐 정보 공개 여부를 바꾸지 않는다.
- `prefers-reduced-motion`에서는 전환 효과를 제거한다.
- JavaScript 오류 시에도 전체 타임라인을 읽을 수 있다.
- 인쇄 매체에서는 모든 활성 상태를 정적으로 적용한다.

### 7.4 설계 카드 동작

- 핵심 3개 판단은 처음부터 요약이 보인다.
- 나머지 판단은 제목과 결론이 보이고 상세 내용만 펼칠 수 있다.
- 버튼은 키보드로 조작 가능하며 `aria-expanded` 상태를 제공한다.
- 인쇄할 때는 상세 내용을 모두 펼친다.

## 8. URL과 PDF 출력

### 일반본

- URL: GitHub Pages 루트 `/`
- PDF: `assets/portfolio/lim-giho-portfolio.pdf`

### 카카오 지원본

- URL: `/applications/2026-08-03/kakaopay-fde/portfolio/`
- PDF: `applications/2026-08-03/kakaopay-fde/portfolio.pdf`

지원 시스템이 URL을 받으면 URL을, PDF만 받으면 해당 프로필의 PDF를 제출한다. 두 출력은 같은 Jekyll 렌더링 결과를 사용한다.

PDF는 A4 세로 방향을 기본으로 한다. 구조도와 설계 카드는 페이지 중간에서 잘리지 않도록 `break-inside` 규칙을 적용한다. 링크는 클릭 가능한 상태를 유지하고, 화면 전용 버튼과 애니메이션은 인쇄 시 제거한다.

## 9. 기존 파일 전환

1. 기존 `_config.yml`에서 포트폴리오 콘텐츠를 새 데이터 파일로 이전한다.
2. 기존 테마 include는 새 포트폴리오 레이아웃에서 사용하지 않는다.
3. `assets/portfolio/architecture.html`의 모델과 설계 판단을 새 데이터 구조로 옮긴다.
4. 통합 결과의 내용과 구조도를 검증한 뒤 standalone `architecture.html`을 삭제한다.
5. `scripts/verify-architecture-portfolio.py`의 유효한 검사 항목은 새 통합 검증기로 옮긴 뒤 삭제한다.
6. 최신 경력기술서 `assets/resume/lim-giho-resume.pdf`는 Hero의 기본 CTA로 유지한다.

## 10. 오류 및 예외 처리

- 존재하지 않는 프로필을 지정하면 빌드 검증을 실패시킨다.
- 프로필이 존재하지 않는 지표나 프로젝트 식별자를 참조하면 검증을 실패시킨다.
- 필수 성과 수치에 출처 메모가 없으면 검증을 실패시킨다.
- 공개 금지어가 렌더링 결과에 남으면 검증을 실패시킨다.
- 외부 링크 오류는 경고로 보고하고, 경력기술서와 내부 페이지 링크 오류는 실패로 처리한다.
- JavaScript가 비활성화되거나 오류가 발생해도 핵심 내용은 숨기지 않는다.
- PDF 생성 실패 시 이전 PDF를 성공 결과로 간주하지 않고 빌드 전체를 실패시킨다.

## 11. 검증 계획

### 정적 검증

- default와 kakao 프로필이 모두 렌더링되는지 확인
- 필수 섹션과 대표 수치 존재 확인
- 프로필 참조 무결성 확인
- 공개 금지어와 실수로 남은 내부 명칭 검사
- 경력기술서, GitHub, 내부 앵커 링크 확인

### 브라우저 검증

- 데스크톱과 모바일에서 섹션 순서와 가독성 확인
- Career Journey가 스크롤에 따라 강조되는지 확인
- 키보드로 설계 카드를 펼치고 닫을 수 있는지 확인
- JavaScript 비활성 상태에서도 모든 핵심 정보가 보이는지 확인
- `prefers-reduced-motion`에서 애니메이션이 제거되는지 확인

### PDF 검증

- default와 kakao PDF를 모두 생성
- A4 페이지 크기 확인
- 잘린 문단, 겹친 카드, 분리된 제목과 본문이 없는지 렌더 이미지로 확인
- 구조도와 핵심 설계 판단이 읽을 수 있는 크기인지 확인
- PDF 내부의 경력기술서와 GitHub 링크가 동작하는지 확인

### Jekyll 검증

- 로컬 프로덕션 빌드 성공
- 생성된 기본 URL과 카카오 URL에 필요한 자산이 포함되는지 확인
- GitHub Pages에서 지원하지 않는 플러그인에 의존하지 않는지 확인

## 12. 완료 조건

- 합의한 정보 구조와 두 테마가 구현되어 있다.

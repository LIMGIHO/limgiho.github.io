- `NestJS가 엔터프라이즈에서 오래 검증된 방식` 같은 일반론은 제거하고 실제 스택 전환 사실만 쓴다.

## 페이지 구성

### 1페이지: 경력 요약과 KWE 주요 업무

- 이름, 소프트웨어 엔지니어, 지원 분야, 연락처
- 2010년부터 이어진 제조 MES와 물류 업무 시스템 경력
- KWE의 15종 이상 레거시를 5개 업무 플랫폼으로 통합한 내용
- 공식 API가 없는 본사 UFS+ 인증·조회·무인 배치 구현
- AI 에이전트와 온프레미스 LLM 적용
- 로컬시스템팀 리더, 팀원 2명
- KWE 주요 업무의 연도별 흐름
- 검증된 대표 결과 네 가지

`이 역할과 맞닿는 지점`이나 이에 준하는 공고 해설 섹션은 넣지 않는다.

### 2페이지: 주요 프로젝트

아래 세 프로젝트를 배치한다.

1. 업무 플랫폼 통합과 본사 시스템 무인 연동
2. AI 에이전트를 이용한 MVP 개발과 요구사항 확인
3. 온프레미스 LLM 기반 문서 처리와 담당 업무 검색

v07의 기술 내용은 유지하되 중복 설명을 줄인다. UFS+ 프로젝트는 인증 흐름 분석, 공통 workflow, 화면·배치 재사용, 데이터 이전 결과를 중심으로 쓴다. AI MVP 프로젝트는 동작하는 화면을 먼저 제공해 데이터 마이그레이션 오류와 현업의 미정 기준을 찾은 내용을 남긴다. Local LLM 프로젝트는 결정적 처리와 의미 해석의 경계, 부분 성공, fallback, 원문 비저장, 사용자 최종 판단을 핵심으로 한다.

AI 사용량 자체를 성과로 쓰지 않는다. 검증되지 않은 개발 시간 단축 수치나 `40개 이상 작업 단위`도 사용하지 않는다.

### 3페이지: 삼성SDS 전세기 프로젝트, 경력과 기술

상단에 삼성SDS 전세기 프로젝트를 배치한다. 이어서 KWE Korea, ILJIN Global 경력, 기술, 기술 전환 경험, 개인 프로젝트를 정리한다.

개인 프로젝트는 다음 세 가지를 포함한다.

- 댓글 필터: MiniLM 임베딩과 WebLLM을 Web Worker에서 실행해 단말 안에서 댓글 분류와 요약 처리
- HealthDog: 운동 기록, 구독 결제와 광고 연동
- 액션톡: 게임 코어 엔진을 도메인 4계층으로 설계

HealthDog와 액션톡은 `기획부터 출시까지 혼자 진행`한 사실을 유지한다. 상세 기술이나 성과는 확인된 내용이 없어 새로 만들지 않는다.

## 삼성SDS 전세기 프로젝트 근거

### 문서와 대조 범위

agent 기록의 테일러 대조표에는 7개 파일 그룹이 있다. One-Set 안의 CI, PL, Summary PL을 각각 문서 유형으로 보면 실제 대조 대상은 9종이다.

1. CI
2. PL
3. Summary PL
4. 일반 원산지증명서
5. FTA 원산지증명서
6. 알루미늄·철강 신고서
7. SAS PO
8. 9 Common Questions
9. Cargo Status

대조표 59행 중 섹션 제목 4개를 제외하면 실질 대조 항목은 55개다.

### 구현 현황

- 자동검증 구현: 19개, 35%
- 값을 읽지만 현업 판단 기준이 없음: 14개, 25%
- 문서 형식 때문에 값을 읽지 못함: 9개, 16%
- 현업 정의 대기: 13개, 24%

합계는 55개다. 19개는 agent 기록에서 구현 완료로 확인된 항목이며, 운영 효과로 표현하지 않는다.

### 업무량 산정

아래 수치는 실측 절감 시간이 아니라 수작업 업무 규모를 설명하기 위한 가정이다.

- 하루 처리량: 20건
- 월 근무일: 20일
- 항목당 육안 확인: 30초
- 문서 열기·전환: 건당 2분 30초

계산 결과:

- 하루 문서 확인: 9종 × 20건 = 180개
- 하루 대조 항목: 55개 × 20건 = 1,100개
- 월 대조 항목: 1,100개 × 20일 = 22,000개
- 건당 수작업 시간: 약 30분
- 월 수작업 업무량: 약 200시간

이력서에는 `월 200시간 절감`이라고 쓰지 않는다. `하루 20건·월 20일·항목당 30초를 가정하면 월 약 200시간 규모`라고 산정 조건을 함께 밝힌다.

### 이력서 문안 방향

다음 내용을 한 문단 또는 두 개의 짧은 항목으로 정리한다.

> 실물 서류 9종의 55개 대조 항목을 분석해 MVP에서 19개 항목의 자동검증을 구현했다. 하루 20건 기준 최대 1,100개, 월 22,000개 항목을 확인하는 업무로, 항목당 30초와 문서 전환 시간을 적용하면 월 약 200시간 규모다. 나머지는 판단 기준 부재 14개, 문서 추출 불가 9개, 현업 정의 대기 13개로 구분해 구현 전에 확인할 예외와 업무 기준을 구체화했다.

공간이 허용되면 다음 근거 중 하나만 보조로 사용한다.

- 설비리스트 1,130행 분석
- PCF 24개 컬럼과 사진 43장 분석 후 Vision 범위를 명판 사진으로 한정

두 수치를 모두 넣어 본문을 과밀하게 만들지 않는다.

## JVM 경험

사용하지 않은 Java와 Kotlin을 기술 목록에 넣지 않는다. 기술 전환 경험에는 아래 사실만 남긴다.

- VB6에서 C#·.NET으로 전환
- C#·.NET에서 Node.js·NestJS로 전환
- 새 코드베이스에서 데이터 흐름, 트랜잭션 경계, 실패 지점을 먼저 확인

JVM 경험 부족을 NestJS의 일반적인 장점으로 우회해서 설명하지 않는다.
